## The tools

### Temporal
A set of tools for doing maths with dates and times: "what date is 14 days after 5 Oct?", "it's 10:00 in Kolkata, what moment is that worldwide?".

- JavaScript's old tool is `Date`. It quietly uses the time zone of whatever computer it runs on, so the same line of code gives one answer on your laptop (India) and another on a server set to London.
- Temporal is the fixed replacement. Not every browser has it built in yet (Safari doesn't, and neither does the Node on your laptop), so we download a copy, `temporal-polyfill`. A *polyfill* is a library that fills in a missing built-in feature.
- Deeper: [[Dates, times and instants]].

### Biome
A program that reads our code *without running it*, points out mistakes and banned patterns (a **linter**), and tidies spacing and quotes (a **formatter**). A grammar checker for code. Run it with `pnpm check`.

- ESLint (the linter) plus Prettier (the formatter) is the older, most common pair. Biome is a newer single tool that replaces both, and it's much faster.
- We've always used Biome; this repo never had ESLint.
- Deeper: [[Tooling choices]].

### The "no `Date` in core" rule
We gave Biome two rules:
1. **Everywhere:** using `Temporal` without importing our downloaded copy is an error. Otherwise the code would rely on the built-in one and crash on Safari.
2. **Only in `packages/core`:** using `Date` at all is an error.

Core is the app's calculator. It gets inputs and returns answers, and it never looks at the clock or the computer's time zone itself. Think of an exam maths question: you're given the numbers; you don't check your watch. The server and the web app may ask "what time is it now?", but they read it and pass it into core.

Here's the second rule in Biome's settings file. The long sentences are the error messages you'd see:

*From `biome.json` (shortened):*
```json
      "includes": ["packages/core/**"],
      // …
                "deniedGlobals": {
                  "Temporal": "Import { Temporal } from 'temporal-polyfill'. Native Temporal is missing in Safari and some Node builds.",
                  "Date": "packages/core is pure: use Temporal from temporal-polyfill, and take `now` as a parameter instead of reading the clock (D-015)."
                }
```

`packages/core/**` means "every file anywhere inside `packages/core`". "Denied globals" are built-in names you're not allowed to use there.

To prove the rule works, a tiny fake file with `new Date()` went into core, Biome ran and complained, and the file was deleted. Like pressing the test button on a smoke alarm.

### TypeScript 7 and Node versions
- **TypeScript** checks our code for mistakes before it runs. Version 7 is the same language with a much faster checker. The plan picked 6 only because ESLint's TypeScript add-on doesn't support 7, and we don't use ESLint. So we switched to 7 on 2026-10-11, after checking it still catches mistakes.
- **Node** is the program that runs JavaScript on a computer (your laptop, the server). Even-numbered versions become **LTS** (long-term support: three years of fixes), which is what servers should run. 24 is LTS now; 26 becomes LTS in late October 2026, and we move to it then. Node's version has nothing to do with the linter.

## How the calendar is built

### A rule
A rule is the repeating pattern of a class:

```
{ freq: 'weekly', interval: 1, byDay: ['MO', 'WE', 'FR'] }   every week on Mon, Wed, Fri
{ freq: 'weekly', interval: 2, byDay: ['TH'] }               every 2 weeks on Thursday (a fortnightly lab)
{ freq: 'daily',  interval: 1 }                              every day (the evening run)
```

A **series** is a rule plus the details: "DBMS, this rule, at 10:00, for 60 minutes, Kolkata time, from 13 July to 27 November".

### A printed timetable plus sticky notes
The app does **not** save every DBMS class of the semester. It saves the rule once (the printed timetable), plus only the things you changed about specific classes (sticky notes on particular days). When the screen wants to show a week, `expand.ts` *calculates* that week's classes from the rules, then applies the sticky notes.

### Layers
Yes, the calendar is built in layers, each one on top of the last:

| Layer | What it is | Example |
|---|---|---|
| 1. Groups and rules | Which classes exist, from the series rules. The group decides the active dates (the semester) and whether holidays apply to it | DBMS Mon/Wed/Fri 10:00, only between 13 Jul and 27 Nov |
| 2. Day exceptions | Holidays and "I'm away" days, one row per day, cancel whole days | 20 Oct is a holiday: every class that day is cancelled, but the "Health" group's run isn't |
| 3. Your changes to one class | Cancel, move, "it's on anyway", and later attendance | DBMS on 7 Oct: prof cancelled |
| 4. Time zone | Turns "10:00 Kolkata" into an exact moment | 10:00 IST = 04:30 world time |

**Precedence** means "who wins when layers disagree": your change on one class beats the holiday, and the holiday beats the rule.

**Tasks are a separate thing** (v1). When you drag a task onto the calendar, it becomes a *block*: a real saved row with a real start and end, not a rule. The screen shows blocks and classes together, but they're stored and calculated separately (D-028).

There's also a *visual* layering on the screen later: cancelled classes are drawn as a faded, striped background, and tasks can sit on top of them (v0.2–v1).

### The window vs the calendar screen
The screen will look like Google Calendar: a 24-hour grid you scroll up and down, a day view on the phone and a week view on desktop (v0.2, `<TimeGrid>`).

The **window** is what the screen asks for behind the scenes. Open the week of 5–11 Oct, and the app asks "give me every class from 5 to 11 Oct": that range is the window. Swipe to next week, and it asks for 12–18 Oct. The window is about *which days*; scrolling is about *which hours* of those days.

The engine draws nothing. It returns a list like "DBMS, Mon 5 Oct, 10:00–11:00", and the grid then draws a box in Monday's column from 10 to 11.

### How a class rescheduled from another week shows up
Say you moved Monday 19 Oct's DBMS class to Saturday 10 Oct, and the screen asks for 5–11 Oct. `expand` works in three passes:

1. **Pass 1, the rule's own dates in the window.** DBMS gives 5, 7 and 9 Oct. For each date, look for a sticky note. 19 Oct isn't in this window, so pass 1 never sees the move.
2. **Pass 2, classes moved in from outside.** Go through every sticky note and ask three questions:
   - Is its *new* date inside the window? 10 Oct: yes.
   - Is its *original* date outside the window? 19 Oct: yes. (If it were inside, pass 1 would already have handled it.)
   - Was there really a DBMS class on the original date? 19 Oct is a Monday: yes.
   
   All yes, so it's added on Saturday 10 Oct, marked "moved".
3. **Pass 3, extra classes** (make-up classes you added): included if their date is in the window.

Then the list is sorted by start time.

The other side: when the screen asks for 19–25 Oct, pass 1 generates 19 Oct, finds the sticky note "moved to 10 Oct", sees that 10 Oct is outside this window, and leaves it out. So the class appears in exactly one place.

Here's the code for pass 2, with what each line asks:

*From `packages/core/src/recurrence/expand.ts` (pass 2, comments added):*
```ts
for (const o of input.overrides) {                                  // every sticky note
  if (o.kind !== 'modified' || o.newDate === null) continue;        // only notes that move a class
  const s = seriesById.get(o.seriesId);
  if (!s) continue;                                                 // its series wasn't asked for
  const original = Temporal.PlainDate.from(o.originalDate);
  if (inWindow(original) || !inWindow(Temporal.PlainDate.from(o.newDate))) continue;
                                                                    // original inside: pass 1 did it
                                                                    // new date outside: not our week
  const g = groupOf(s);
  if (!occursOn(s, original, g)) continue;                          // no real class on the original date
  out.push(resolve(s, g, original, o, days));                       // add it at its new place
}
```

One requirement for later: when the server loads sticky notes from the database (v0.2), it must fetch notes whose *new* date is in the window, not only their original date. Otherwise pass 2 never gets to see them.

## Every class has an identity, even though it isn't saved

You asked: "if classes are only calculated, how can attendance or notes attach to one?"

**Each class has a permanent name**, built from its series and its *original* date: `dbms:2026-10-07` is "the DBMS class the rule put on 7 October". The app computes the same name every time, so it works like an ID even though no row exists.

The code that makes the name is two lines: stick the series id, a colon and the date together.

*From `packages/core/src/recurrence/keys.ts` (shortened):*
```ts
export const occurrenceKey = (seriesId: string, originalDate: ISODate): OccurrenceKey =>
  `${seriesId}:${originalDate}`;
```

(In the real app the series id is a long random-looking code rather than `dbms`, but the idea is the same.)

**A class gets a saved row the moment you say something about it.** Cancel it, move it, or (in v2) mark that you attended, and the app saves a sticky note in the `occurrence_override` table under that name. Classes you never touch stay purely calculated. Next time the week is calculated, the engine finds the sticky note by name and applies it.

- **Why the original date, not the time:** if DBMS later moves from 10:00 to 10:30 for the rest of term, `dbms:2026-10-07` is still the same name, so your notes stay attached.
- **Attendance (v2):** a sticky note can hold `confirmedAt` ("I went", saved from the evening review). A cancelled note says *why*: `skipped` (I didn't go) or `not_held` (the prof cancelled, or a holiday). The percentage comes from counting a subject's classes up to today and checking their sticky notes. Today the engine already passes `confirmedAt` through; the counting arrives in v2.
- **Notes on one class:** added on 2026-10-12. The sticky note has a free-text `note` field ("Bring the lab manual"). See "Notes on one class" at the end.

**"Aren't past classes their own entity once they're done?"** Not in this design. Past classes are recalculated from the rule every time, exactly like future ones. That's why changing the rule would rewrite the past, and why `split.ts` exists: it *ends* the old rule the day before the change, so nothing in the past is ever calculated from the new rule.

The other way is to save a real row for every class of the semester ("materialising"). Then each class is its own entity, and you can attach anything to it directly. The costs:
- "Move all future DBMS classes to 11:00" means finding and updating dozens of rows.
- A daily habit with no end date needs a background job that keeps creating rows forever.
- The rule and the rows can drift apart: two sources of truth.

Rules plus sticky notes is what Google Calendar and the iCalendar standard do. It was decided as D-021, and the trade-offs are in `docs/brainstorm/01` §3–4.

## Changing the timetable mid-semester: `split.ts`
"From next Monday, DBMS is at 11:00 instead of 10:00." Editing the series directly would rewrite history: past classes would show 11:00, and if the day changed (Monday → Tuesday), past Monday classes would vanish and the attendance count would break.

So `split.ts` closes the old series the day before the change, and starts a new series from that date with the new time. It also moves sticky notes you'd already made on future classes over to the new series. If the new timetable no longer has a class on that day, it lists the note so the app can warn you ("this change won't apply any more"). No screen uses it until v0.3b. Deeper: [[Recurrence engine]].

## Daylight saving
Some countries move their clocks an hour forward in spring and back in autumn; India doesn't. On one March night in New York, 1:59 jumps to 3:00, so **2:30 doesn't exist**. In autumn, 1:30 happens **twice**. For a class "every day at 2:30, New York time", we show it at 3:30 on that night and mark it as shifted, instead of silently dropping it. You'll never hit this in India, but it keeps the app correct if you travel, or someone abroad uses it. Deeper: [[Time zones and daylight saving]].

## "+05:30" vs "Asia/Kolkata"
- A **name** like `Asia/Kolkata` or `America/New_York` carries the zone's full rules: Kolkata is always 5½ hours ahead of world time, while New York is 5 hours behind in winter and 4 in summer.
- A **fixed number** like `+05:30` never changes. For India it means the same thing, but a New York class saved as `-05:00` would be an hour wrong all summer.
- Temporal accepts fixed numbers as a zone, so the engine refuses them itself. Only names get saved.

## The tests

### Golden weeks
A **golden file** is a saved copy of the correct output, checked by a person once. Each test run produces the output again and compares, and any difference fails the test. The engine was given a made-up, KIIT-shaped timetable (your real one stays private; see "Your timetable as data" at the end) and asked for two weeks: one normal, and one with a holiday, a moved class, a rescheduled lab and a make-up class. The results are saved as readable text in `packages/core/src/recurrence/__snapshots__/`, and every line was checked by hand.

### Breaking the code on purpose
A test is only useful if it **fails when the code is wrong**. To check ours, pass 2 (the "moved in from another week" step) was disabled and the tests run. Three failed, so they noticed. Then the code was restored exactly. Like testing a smoke alarm with a lit match.

One of the three: a test asks for "1–31 Oct" at once, then for "1–15" and "16–31" separately, and checks both give the same classes, 1,000 times with random made-up timetables. With pass 2 off, a class moved from 10 Oct to 20 Oct went missing in the two-halves version. Deeper: [[Testing pure code]].

## Your decision: reschedules beat holidays
If you reschedule a class onto a day, you're saying it happens, holiday or not, and the app treats it that way. The one leftover case: you change a class's time today, and *later* that day is declared a holiday. The app can't know which came first, so cancel that one class by hand. ## Follow-up questions (2026-10-11)

### What a "sticky note" is
It's our nickname for **one row in the `occurrence_override` table**. Its type in code is `OccurrenceOverride` (in `types.ts`). It's saved only when you do something to one specific class, and it's filed under that class's name (`dbms:2026-10-07`).

### Do groups have layers among themselves?
No. Groups sit **side by side**, like separate tracks. Each group's classes are worked out on their own, then everything is merged into one list sorted by time, and no group overrides another. Group settings change only that group's own classes: "observes holidays" decides whether a holiday cancels them, and "attendance" decides whether skipping asks "Prof cancelled / I skipped".

If two groups have something at the same time (a lab and the evening run), both show, side by side in the grid. Nothing is hidden. From v0.3b, the app warns when a new group clashes with an existing one (D-029).

### Are tasks saved as entities?
Yes. A task ("Finish DBMS assignment") is a row in a `task` table. When you plan it on the calendar, a **block** row is saved: which task, start, end. Tasks are one-offs with no pattern to calculate from, so each one is simply stored (v1, D-028).

### "Which series plus which date is the id; save only what's attached, calculate the rest"
Exactly right. The name is *which series* + *which date the rule put it on*. Anything you attach is saved under that name, and everything else is calculated when the screen asks.

### "Use `<series>:<date>` as the id for anything we attach"
The **filing system** already works this way: while the engine calculates a class, it builds that name and looks up the sticky note filed under it.

On 2026-10-11 the **text field was missing**. A sticky note could only hold these:
- cancelled, and why;
- moved to another date or time;
- a different length;
- `confirmedAt` (attendance).

There was no box for words like "bring the lab manual". Adding one meant adding **one field** (`note`) to the same sticky note: no new table, no new name and no new lookup, because the engine already finds the right sticky note. It was added the next day; see "Notes on one class" below.

A note on a **whole day** ("dentist at 5") doesn't fit here. In this app's words that's a **block**: one-off planned time you create yourself, like a Google Calendar event, saved as its own row (v1; the design docs use exactly "Dentist" as the example). A **session** is something else: time you actually tracked with the timer.

One refinement in the database: the name is stored as **two columns**, `series_id` and `original_date`, with a rule that the pair is unique. Two reasons:
- The database can ask "all sticky notes in October" quickly, using an index on the date.
- It can refuse a sticky note for a series that doesn't exist (a *foreign key*).

The app and the API still use the joined string `dbms:2026-10-07`.

**One row, or one table per kind of info?** Today, everything about one class (cancelled, moved, attended, a note) lives in **one** row, with an empty field meaning "nothing said". The other option is one table per kind of info (attendance, notes, moves), all using the same name. That's more flexible, but every week's calculation would read several tables. One row is simpler while there are only a few kinds of info.

**Two levels of attached info:**
- **Per class:** a sticky note on `dbms:2026-10-07`.
- **Per whole day:** a day exception on `2026-10-20` (a holiday), which affects every class that day in groups that observe holidays.

### How attendance actually works (your D-005 and D-010)
The earlier line, "a sticky note can say *I went*", made it sound like you tick every class. You don't.
- **Optional, per group:** each group has an attendance on/off switch. Classes on, Health off. It's not one app-wide setting.
- **The default is "attended"** (D-005). You only act on exceptions: cancelling a class asks once, "Prof cancelled" or "I skipped", and that cancel is a sticky note.
- **The evening check** (D-010, your fix for D-005's gap): forget to mark a skip, and default-attended quietly inflates your percentage. So the evening shutdown lists today's classes **already ticked as "went"**. You flip any you skipped and close it: one tap on a normal day. Closing it saves `confirmedAt` on today's classes.
- **Not reviewed yet** means "unconfirmed", so attendance shows as a range ("75–90%, 3 to confirm") until you review.

A side effect: in attendance groups, every class you confirm ends up with a small row anyway. That's fine; see below.

### "Saving each class would waste space and be slow"
The right conclusion, but those aren't the real reasons.
- **Space:** about 30 classes a week × 20 weeks ≈ 600 rows a semester, roughly 100 KB. For Postgres that's nothing.
- **Speed:** reading a week's 30 rows from an indexed table takes about a millisecond. That's as fast as calculating them, maybe faster.
- **The real reasons are about staying correct:**
  - "All DBMS from 11:00" would mean updating dozens of rows, and missing one leaves a wrong class.
  - A daily habit with no end date needs a background job creating rows forever.
  - A holiday added later has to be applied to every saved row.
  - The rule and the rows can disagree, and then which one is true?

  With rules plus sticky notes there's one source of truth, so these bugs can't happen.

### Notes on one class (added 2026-10-12)
You asked for it, so the sticky note now has a `note` field: free text such as "Bring the lab manual".
- **Where it's saved:** in the same sticky note as everything else about that class, under the same name (`dsl:2026-10-05`). A class with only a note gets a sticky note with every other field empty.
- **What the calendar gets:** each calculated class now has `note`, either the text or `null` for "no note".
- **A note never changes the class.** It doesn't move it, cancel it, or keep it on. Example: Economics on 20 Oct has the note "Essay still due today", and the holiday still cancels the class. The note still shows, so you see it on the cancelled class.
- **Extras can have notes too:** a make-up class with "Room changed to C-105".
- **Splits keep them:** when `split.ts` moves your sticky notes to the new series, the note travels with the rest of the row.
- **Not decided yet: a length limit.** The engine passes the text through as it is. The database and the API (v0.2) will cap it; the session notes in the design use 4,000 characters.

How it's tested:
- one test per case above (a normal class, a class moved in from another week, an extra, a class on a holiday);
- a property test, "notes are inert": in 1,000 random timetables, put a note on every sticky note, and check that nothing else about any class changes;
- the two golden weeks now each show a note, one of them on the holiday-cancelled Economics class;
- the "break it on purpose" check: making the engine drop every note failed six tests.

### Your timetable as data (2026-10-12)
You sent your section's printed grid. Here's how one cell becomes something the engine understands. (The examples here use the made-up sample timetable, not your real one, because this vault is public.)

**Each cell is a "slot":** weekday, start, end, subject, room. The sample's Monday 08:00 Data Structures cell is `{ day: 'MO', start: '08:00', end: '09:00', title: 'DS', room: 'C-301' }`. The fixture (now `private/kiit-sem3.ts`) is just your grid written out like that, one line per cell, so you can check it against the image row by row.

**Each slot becomes its own series**, repeating weekly. Why not one series per subject? A series has *one* start time and *one* room, and a subject can meet at a different time and room every day. Say a made-up Compilers class (CD) meets Mon 10:00 in C-101, Tue 12:00 in C-204, Wed 11:00 in C-105 and Thu 12:00 in C-301. Then CD is four series (`cd-mo`, `cd-tu`, `cd-we`, `cd-th`), all with `subject: 'CD'`. The subject ties them back together, so attendance (v2) counts "CD" as one subject.

**Two-period labs are one block.** A lab that fills two periods back to back (the sample's Data Structures Lab, Monday 14:00 and 15:00) is one 120-minute class, not two 60-minute ones. You confirmed KIIT counts a 2-period lab as **one** attendance, so one class is also right for the attendance count (v2).

**What's real and what's made up:** the slots are your real timetable. The changes in it are invented to exercise the engine: a class cancelled, a holiday, a class moved to Saturday, and so on. You confirmed the semester's first day. The end isn't fixed, so the group has no end date; archiving it at the end of term sets one (D-030). Each series' `subject` is now the full name ("Data Structures"), and the title stays the short code you see on the printed grid ("DS").

**Where it lives: `private/`, never in git.** The repo is public, and a timetable says where you are at every hour, so you asked to keep it private. It was committed locally once, then removed from the branch before anything was pushed, and moved to `private/` (`kiit-sem3.ts` plus the two weeks it produced, both checked by hand). `.gitignore` lists `private/`, so git never picks it up. The public tests keep the made-up sample.

**Public code is not public data.** GitHub holds the *code*. Your timetable will live in the *database* on your server, behind your login. Nobody reads it from GitHub, because it's never there.
